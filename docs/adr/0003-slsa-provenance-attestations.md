# 0003 — SLSA provenance via GitHub Artifact Attestations

Status: accepted

## Context

pqscan is a security tool whose whole distribution channel is a **binary**
(the PD-ecosystem contract in
[`docs/spec.md#5-feature-set`](../../blob/main/docs/spec.md#5-feature-set):
single static binary). Every published artifact therefore needs verifiable
build provenance: operators run it from CI logs and Homebrew taps, and
post-quantum readiness verdicts from this tool are audit-grade — the
provenance chain must be, too.

GitHub Artifact Attestations generates signed SLSA build provenance for
 artifacts built in Actions: keyless Sigstore signing against the
repository/OID issuer, verifiable with `gh attestation verify` (or
`slsa-verifier`) offline. OpenSSF Scorecard monitors the posture
continuously; Dependency Review guards dependency diffs (already live).

## Decision

1. Every artifact this project publishes — release binaries (M5, goreleaser)
   and the intermediate per-push CI builds — carries SLSA provenance
   generated by `actions/attest-build-provenance` in the same job that
   produces the artifact (no post-hoc wrapping).
2. Governance documentation (site governance page, SECURITY supply-chain
   section) states the verification command and subject predicate so
   operators can verify a binary *before* running it.
3. OpenSSF Scorecard runs weekly on a SHA-pinned workflow and publishes
   publicly (badge lands with the release milestone).
4. The posture target is SLSA Build L3 shape (isolated, provenance,
   non-falsifiable runner); goreleaser at M5 integrates attestation into
   the release job rather than shipping unsigned release assets.

## Consequences

- Operators verify with (subject digest bound to the release):

```
gh attestation verify <artifact> -R shsingh/pqscan
```

- CI build jobs gain `id-token: write` (keyless signing needs it) — the
  blast radius of a compromised job is unchanged (it could already sign
  as the workflow identity); provenance becomes forgery-evident.
- Release tooling at M5 must wire attestations *before* the first release
  binary ships; an unsigned release binary is a release-blocker, not a
  follow-up.
- The intermediate per-push attestation gives the M0/M1 lanes a verification
  workflow that never depends on release artefacts existing.
